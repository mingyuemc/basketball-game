## 一、项目概述

### 1.1 产品定位

Hoops Arena 是一款**浏览器端多人在线 3D 篮球竞技游戏**，支持 3v3 实时对战（引擎能力支持扩展至 4v4）。玩家操控一名球员，与队友配合完成进攻与防守，在标准半场进行比赛。

### 1.2 核心设计目标

| 目标 | 衡量标准 |
|------|----------|
| **低门槛** | 打开浏览器即玩，无需下载客户端，3 分钟完成一局 |
| **强竞技** | 网络延迟感知 < 120ms，操作响应即时 |
| **高帧率** | 桌面端稳定 60 FPS，移动端 ≥ 30 FPS |
| **公平性** | 服务端权威判定，杜绝位置/命中作弊 |
| **零成本** | 全栈使用 GitHub + Cloudflare 免费额度，月支出 0 元 |

### 1.3 目标用户

- 篮球游戏爱好者（NBA 2K / NBA Jam 用户）
- 休闲竞技玩家（碎片化时间，单局 3-5 分钟）
- 移动端轻度玩家

### 1.4 玩法模式

| 模式 | 人数 | 说明 |
|------|------|------|
| **快速匹配 3v3** | 6 人 | 核心模式，半场 3v3 对战 |
| **1v1 斗牛** | 2 人 | 一对一单挑，先得 11 分胜 |
| **训练场** | 1 人 | 单人练习投篮/运球，无网络压力 |
| **自定义房间** | 2-8 人 | 邀请好友自定义规则 |

### 1.5 零成本约束下的设计原则

> 本项目的首要工程约束是 **"一分钱不花"**，所有架构决策都优先适配 Cloudflare 免费额度与 GitHub 免费服务。三条核心原则：

1. **边缘优先**：把逻辑放到 Cloudflare 边缘（Workers / Durable Objects），用免费额度替代服务器租赁。
2. **轻量化权威**：服务端只做"关键判定"，不做全量刚体物理，以适配 Workers 的 CPU 时间限制。
3. **无 TURN 依赖**：不使用 WebRTC P2P（TURN 中继不免费），全部走 Cloudflare WebSocket 中继。

### 2.4 选型对比说明

**为什么放弃 Node.js + Colyseus + Redis + PostgreSQL + K8s？**

| 原方案 | 问题 | 新方案（免费） |
|--------|------|----------------|
| Node.js 服务器 | 需要租云主机（$5-20/月） | Cloudflare Durable Objects |
| Redis | 需自建或付费托管 | Cloudflare KV |
| PostgreSQL | 需付费托管（$10+/月） | Cloudflare D1 |
| WebRTC + TURN | TURN 中继不免费 | 全走 WebSocket 中继 |
| Docker + K8s | 集群成本高 | Serverless，零运维 |
| 对象存储 | S3 出流量贵 | R2 零出流量费 |

**为什么用 Rapier 而非 cannon-es？**
- Rapier 基于 Rust 编译为 WASM，性能约为 cannon-es 的 3-5 倍
- Rapier 支持确定性模拟，保证客户端预测与服务端判定一致

**为什么不用 Unity WebGL / Godot？**
- Unity WebGL 包体积大（10MB+），首屏加载慢，移动端性能差
- Three.js 包体可控，加载快，符合"打开即玩"定位

## 五、多人网络架构

### 5.1 网络模型

**采用"Cloudflare 边缘权威 + 客户端预测 + 服务器回滚"架构，全 WebSocket 通信（不使用 WebRTC）。**

```
┌──────────┐                            ┌──────────────────┐
│  客户端   │  ① 输入 (Input, 20Hz)      │ Durable Object   │
│  Client  │ ─────────────────────────▶ │  (房间 = 1 DO)    │
│          │                            │                  │
│  ② 预测   │  ④ 权威状态 (Snapshot)     │  ③ 轻量权威模拟   │
│  本地模拟 │ ◀───────────────────────── │  20Hz Tick       │
│          │                            │  关键判定 + 回滚  │
│  ⑤ 回滚   │                            │                  │
│  与和解   │                            │  WebSocket 休眠   │
└──────────┘                            └──────────────────┘
```

| 技术 | 作用 |
|------|------|
| **客户端预测** | 本地立即响应输入，消除延迟感 |
| **边缘权威** | Durable Object 内判定进球/抢断/盖帽，防作弊 |
| **延迟补偿** | DO 回溯历史状态，正确处理"过去的投篮" |
| **状态和解** | 服务端状态与预测不符时回滚重放 |
| **插值** | 远端玩家位置平滑渲染 |

### 5.2 为什么不用 WebRTC？

| 方案 | 问题 |
|------|------|
| WebRTC P2P 直连 | 部分网络（NAT 严格）无法建立连接 |
| WebRTC + TURN 中继 | **TURN 服务器需要付费**，违背零成本约束 |
| **Cloudflare WebSocket 中继（选用）** | DO 免费额度内可支撑，延迟可控，架构简单 |

> 所有流量经由 Cloudflare 边缘中继，虽然多一跳，但在全球边缘网络下延迟可控，且换来**零成本 + 零运维 + 全方位反作弊**。

### 5.3 同步频率策略（适配免费额度）

| 数据 | 频率 | 策略 |
|------|------|------|
| 玩家输入（上行） | 20 Hz | 立即发送（降低频率以省 DO 消息额度） |
| 球员位置/旋转 | 15 Hz | 增量广播 |
| 篮球物理 | 20 Hz | 权威模拟 + 插值 |
| 比赛事件（进球/犯规） | 事件触发 | 可靠传输 |
| 全量状态快照 | 5 Hz | 和解校验 |

> **频率取值的权衡**：免费额度与游戏流畅度的平衡点。20Hz 输入 + 插值渲染对休闲篮球游戏足够；实测若体验不足，可通过"仅对持球人高频、其他人低频"优化。

### 5.4 客户端预测流程

```
帧 N:
1. 采集本地输入 Input_N，加入本地输入缓冲
2. 立即用确定性物理模拟，更新本地球员位置 (预测)
3. 将 Input_N 发送到 DO

收到 DO 状态快照 (含 ack 的 Input 序号 M):
4. 服务端状态 = Snapshot
5. 丢弃本地输入缓冲中 ≤ M 的输入
6. 本地状态重置为服务端状态
7. 重放 (Replay) 缓冲中 > M 的输入，重新模拟到当前帧
8. 若差异 > 阈值 → 平滑插值修正
```

### 5.5 延迟补偿（投篮判定）

Durable Object 用内存环形缓冲保存过去 1 秒状态历史。收到投篮输入时：

```
1. DO 记录该输入的时间戳 T
2. 从历史缓冲回溯到 T 时刻场景状态
3. 在 T 时刻场景中判定：是否被盖帽 / 投篮干扰程度
4. 采样命中结果（基于命中率公式 + 随机种子，种子由服务端下发）
5. 将结果应用到当前世界
```

> 解决"我看到空位投篮，服务端却判定被盖帽"的经典问题。

### 5.6 网络质量适配

| RTT 区间 | 策略 |
|----------|------|
| < 50ms | 全速预测，无插值延迟 |
| 50-150ms | 标准预测 + 插值缓冲 100ms |
| 150-300ms | 插值缓冲增至 200ms |
| > 300ms | 提示网络不佳，建议降低画质/换网络 |

**丢包处理**：全部走 WebSocket（TCP），天然可靠传输，不丢包；代价是丢包时会短暂阻塞（对休闲篮球可接受）。

| 跳跃/盖帽 | 空格 | Y 键 | 跳跃按钮 |
| 换防切换 | Q 键 | LB | 切换按钮 |

### 6.2 投篮机制（核心）

**蓄力投篮系统**：

```
按键时长 → 蓄力值 → 出手时机判定
┌──────────────────────────────────────┐
│  短按 ────── 完美点 ────── 长按        │
│  (力量不足)   (命中率高)   (力量过大)  │
│  ▁▃▅▇█████████▇▅▃▁                    │
│            ▲                          │
│         完美释放区间                   │
└──────────────────────────────────────┘
```

**命中率计算模型**：

```
HitChance = BaseAccuracy          // 球员基础属性 (0.5-0.9)
          × ReleaseTimingFactor   // 释放时机 (±30%)
          × DefenderPressure      // 防守干扰 (0.4-1.0)
          × DistanceFactor        // 距离衰减
          × StaminaFactor         // 体力影响 (0.7-1.0)
          × PerfectReleaseBonus   // 完美释放 +15%

最终概率范围: [0.05, 0.95]，保留随机性
```

**混合模型（关键，为适配免费额度设计）**：
- 球飞行的**视觉轨迹**由客户端真实物理模拟（抛物线、碰撞），观感真实
- **是否命中**由服务端用上式**概率采样**决定（服务端只需算概率，无需算全量刚体物理）
- 服务端下发随机种子，客户端据此生成轨迹微扰，两端结果一致

> 这是适配 Workers CPU 限制的核心技巧：**把"重物理"放客户端，"轻判定"放边缘**，既省算力又能反作弊。

### 6.3 防守机制

| 行为 | 效果 |
|------|------|
| **贴身防守** | 距离 < 1.5m 时，降低对手命中率 20-40% |
| **盖帽 (Block)** | 跳跃时机正确且手部触及球 → 拍飞篮球 |
| **抢断 (Steal)** | 从运球者手中拨走球，成功率受双方属性影响 |
| **抢篮板 (Rebound)** | 球不进时，跳跃最高/卡位最优者抢到球 |

|------|-----|
| 比赛时长 | 单节 3 分钟（快速模式）或 2 节 × 3 分钟 |
| 进攻时限 | 24 秒 |
| 半场时限 | 8 秒（后场推进） |
| 三分线距离 | 6.75m（弧顶） |
| 得分 | 两分球 / 三分球 / 罚球 |

### 7.4 DO 端轻量判定（伪代码）

```typescript
// 每个 tick 在 Durable Object 内执行（目标 CPU < 10ms）
tick() {
  // 1. 校验球员位置合法性（是否超速/瞬移）
  for (const p of this.players) {
    if (dist(p.reportedPos, p.lastPos) > MAX_SPEED * dt * 1.15) {
      p.reportedPos = clampToMaxSpeed(p.lastPos, p.reportedPos); // 纠正
      this.flagSuspicious(p.id);
    }
  }
  // 2. 判定球权 / 出界 / 24秒违例（纯几何 + 计时，开销极低）
  this.updatePossession();
  this.updateClock();
  // 3. 若有投篮事件，做概率采样（一次随机数，开销极低）
  for (const shot of this.pendingShots) {
    const chance = calcHitChance(shot, this.players);
    const made = this.rng() < chance;   // 服务端种子驱动，可复现
    this.resolveShot(shot, made);
  }
  // 4. 广播增量状态
  this.broadcastSnapshot();
}
```

### 7.5 确定性保障

- 客户端物理使用固定步长 `1/60`，绝不使用可变 dt
- 关键随机使用服务端下发的种子 + 客户端/服务端相同的 PRNG 算法
- DO 与客户端共享 `shared/math/` 定点数运算，避免浮点差异

## 九、网络协议设计

### 9.1 二进制协议格式

使用紧凑二进制而非 JSON，减少带宽（约为 JSON 的 1/5）——**同时直接降低 DO 出流量与时长消耗**。

**消息头部（4 字节）**：

```
┌──────────┬──────────┬────────────────────┐
│ MsgType  │  Seq     │  Length            │
│ (1 byte) │ (1 byte) │  (2 bytes)         │
└──────────┴──────────┴────────────────────┘
```

### 9.2 消息类型定义

| 类型 ID | 名称 | 方向 | 说明 |
|---------|------|------|------|
| 0x01 | `C_INPUT` | C→S | 玩家输入（移动/动作） |
| 0x02 | `C_JOIN` | C→S | 加入房间 |
| 0x03 | `C_READY` | C→S | 准备就绪 |
| 0x11 | `S_SNAPSHOT` | S→C | 全量状态快照 |
| 0x12 | `S_DELTA` | S→C | 增量状态 |
| 0x13 | `S_EVENT` | S→C | 事件（进球/犯规） |
| 0x14 | `S_MATCH_STATE` | S→C | 比赛状态变更 |
| 0x15 | `S_SEED` | S→C | 随机种子下发 |

### 9.3 玩家输入包结构

```
C_INPUT (20Hz):
┌────────┬────────┬──────────┬──────────┬──────────┐
│ Seq    │ MoveX  │ MoveZ    │ Actions  │ Tick     │
│ uint16 │ int8   │ int8     │ uint8    │ uint32   │
└────────┴────────┴──────────┴──────────┴──────────┘
共 10 字节/输入 → 20Hz 下约 200 B/s

Actions 位掩码:
bit 0: 冲刺   bit 1: 投篮蓄力中   bit 2: 投篮释放
bit 3: 传球   bit 4: 抢断         bit 5: 跳跃/盖帽
```

### 9.4 状态快照包结构

```
S_SNAPSHOT (15Hz):
┌─────────┬─────────────────────────────────────────┐
│ Tick    │ Players[]                                │
│ uint32  │  ├─ id (uint16)                          │
│         │  ├─ pos (3×float16 = 6B)                 │
│         │  ├─ rot (int16 压缩 = 2B)                │
│         │  ├─ animState (uint8)                    │
│         │  └─ flags (uint8: 持球/跳跃/体力)         │
│         │ Ball                                     │
│         │  ├─ pos (6B) + vel (6B) + spin (4B)      │
│         └─ AckedInputSeq (uint16)                  │
└─────────┴─────────────────────────────────────────┘

单个球员 ≈ 12 字节，6 人 + 球 ≈ 92 字节/快照
15Hz → 约 1.4 KB/s 下行（每人）
```

## 十、服务端架构（Durable Objects）

### 10.1 Durable Object 房间模型

**一个房间 = 一个 Durable Object 实例**（全局唯一 ID = 房间号）。

```
DurableObject: MatchRoom
┌─────────────────────────────────────────────────┐
│  状态存储 (SQLite-backed, 免费计划可用):          │
│  storage.sql: 比赛记录、玩家席位、计分           │
│                                                 │
│  WebSocket 连接池:                               │
│  ├─ 玩家A 连接                                   │
│  ├─ 玩家B 连接                                   │
│  └─ ... (最多 6 人)                              │
│                                                 │
│  WebSocket Hibernation (休眠 API):               │
│  ├─ 无消息时 DO 休眠 → 不计费                    │
│  └─ 收到消息 → 唤醒处理 → 再休眠                  │
│                                                 │
│  模拟循环 (alarm 或 setInterval):                │
│  ├─ 每 50ms (20Hz) 执行 tick()                   │
│  ├─ 轻量判定 (见 7.4)                            │
│  └─ 广播增量快照                                 │
└─────────────────────────────────────────────────┘
```

### 10.2 关键：WebSocket Hibernation

Cloudflare Durable Objects 支持 **WebSocket 休眠**：

- 连接保持，但 DO 实例不在内存中 → **不消耗持续时间额度**
- 收到消息时自动唤醒
- 通过 `webSocketMessage` / `webSocketClose` 事件处理
- 使用 `state.acceptWebSocket(server)` 注册可休眠连接

> 这是让免费额度支撑实时游戏的**核心机制**——避免 DO 因长连接常驻内存而耗尽免费时长。

### 10.3 房间生命周期

```typescript
export class MatchRoom implements DurableObject {
  async fetch(request: Request) {
    const pair = new WebSocketPair();
    this.ctx.acceptWebSocket(pair[1]);   // 注册可休眠连接
    return new Response(null, { status: 101, webSocket: pair[0] });
  }
  async webSocketMessage(ws, msg) { /* 处理输入 */ }
  async webSocketClose(ws) { /* AI 托管或移除 */ }
  async alarm() { /* 20Hz 模拟 tick */ }
}
```

### 10.4 后端服务划分

| 服务 | 实现 | 职责 |
|------|------|------|
| `api` Worker | Hono 框架 + Workers | 登录、房间列表、战绩 API |
| `MatchRoom` DO | Durable Object | 单房间实时对战 |
| `Matchmaker` DO | Durable Object（单例） | 匹配队列调度 |

### 10.5 免费额度下的容量估算

| 资源 | 免费额度 | 估算消耗 | 可支撑 |
|------|----------|----------|--------|
| Workers 请求 | 10 万/天 | API 调用 | 数万次登录/查询 |

## 十一、匹配与房间系统

### 11.1 匹配流程（基于 KV + Durable Object）

```
玩家点击"快速匹配"
  │
  ├─ 1. Worker 读取玩家 MMR（从 D1）
  ├─ 2. 写入匹配队列：KV 存 "queue:{bucket}" → 玩家列表
  │      （为省 KV 写入额度，队列可用 Matchmaker DO 内存维护）
  ├─ 3. Matchmaker DO 每 2 秒扫描一次队列
  │     ├─ 找同 MMR 桶内 6 名玩家 → 组队
  │     └─ 等待 > 15s 未满 → 扩大 MMR 范围 ±200，或 AI 补位
  ├─ 4. 队伍平衡算法（按 MMR + 位置偏好分配）
  ├─ 5. 通过 DO idFromName(roomId) 生成房间 DO
  ├─ 6. 下发房间信息（WSS 地址 + 房间 token）
  └─ 7. 客户端连接房间 DO，进入选人/准备
```

> **省额度技巧**：匹配队列优先用 **Matchmaker DO 的内存**维护（不占 KV 写入额度），仅在 DO 重启时用 KV 兜底持久化。

### 11.2 MMR 计算（Elo 变体）

```
预期胜率 E = 1 / (1 + 10^((对手MMR - 我的MMR) / 400))
新MMR = 旧MMR + K × (实际结果 - E)

K 值：新手 40，普通 32，高手 16（随场次递减）
队伍 MMR = 全队平均，按队伍平均计算胜负
```

### 11.3 房间状态

```typescript
  id: string;
  status: 'waiting' | 'picking' | 'playing' | 'ended';
  players: PlayerSlot[];       // 最多 6 席
  teamA: string[];             // 队伍A 玩家ID
  teamB: string[];             // 队伍B 玩家ID
  matchClock: number;
  score: { a: number; b: number };
  seed: number;                // 随机种子（用于确定性判定）
}
```

## 十二、反作弊与安全

### 12.1 边缘权威原则

| 数据 | 权威方 | 说明 |
|------|--------|------|
| 命中判定 | Durable Object | 概率采样在边缘完成，种子不下发给客户端前先算结果 |
| 得分 | Durable Object | 由边缘规则引擎决定 |
| 计时 | Durable Object | 客户端时钟仅用于显示 |
| 位置 | 客户端 + 校验 | 客户端上报，边缘校验速度上限并纠正 |
| 球权/出界 | Durable Object | 纯几何判定，开销低 |

### 12.2 常见作弊与防护

| 作弊类型 | 防护手段 |
|----------|----------|
| **速度修改（加速挂）** | DO 校验位移上限，超限回弹并标记 |
| **自动瞄准** | 校验投篮输入时间差、鼠标轨迹自然度 |
| **命中作弊** | 命中由 DO 概率采样决定，客户端无法伪造 |
| **位置瞬移** | 位移超过理论最大值 → 拒绝并回滚 |
| **数据包篡改** | 二进制协议 + 输入合法性校验 + 房间 token |
| **多开刷分** | Cloudflare Turnstile + 设备指纹 + IP 限制 |
| **机器人注册** | Turnstile 人机验证（免费） |

### 12.3 输入合法性校验（DO 内）

```typescript
function validateInput(player, input, dt) {
  // 1. 移动速度校验
  const maxSpeed = player.sprint ? 8.5 : 5.5; // m/s
  const maxDist = maxSpeed * dt * 1.15;        // 15% 容差
  if (input.moveMagnitude * dt * maxSpeed > maxDist) {
    return REJECT_AND_CORRECT;
  }
  // 2. 动作冷却校验
  if (input.action === 'shoot' && player.shootCooldown > 0) return REJECT;
  // 3. 时序校验
  if (Math.abs(input.tick - serverTick) > 15) return SUSPICIOUS;
  return ACCEPT;
}
```
